# DESIGN_PRINCIPLES

## 文档目标

本文件用于约束 `java-upgrade-analyzer` 的开发和维护，不用于指导 Claude Code 在运行时如何使用该 Skill。

本文件的目标是把本工程的定位、结构边界、状态管理、参数来源、交互恢复协议等核心原则固定下来，避免后续实现为了局部便利而偏离整体设计。

涉及以下范围的改动时，必须先满足本文件，再讨论具体实现：

- 工程目录结构
- 核心文件职责
- 状态管理
- 参数读取与传递
- 待交互中断与恢复
- 调度入口与步骤编排

## 工程定位

`java-upgrade-analyzer` 是一个供 Claude Code 使用的 Skill 工程，不是普通业务应用，也不是普通脚本集合。

该工程的职责是为 Claude Code 提供 Java 升级兼容性分析能力，包括但不限于：

- 分步执行
- 门控与阻塞
- 待交互中断
- 恢复执行
- 证据产物生成
- 最终报告汇总

本工程的设计、目录结构、关键文件职责、入口组织方式，必须遵循 Claude Code 对 Skill 工程的要求。若当前实现与 Claude Code 对 Skill 的要求不一致，应以后者为准进行整理。

## 文档职责边界

本工程中不同文档的职责必须明确分离，不得混用：

- `SKILL.md`
  - 面向 Claude Code 在使用该 Skill 时读取。
  - 只承载 Skill 的运行期规则、交互规则、执行边界。
  - 其职责定义应参考 Claude Code 对 Skill 的说明。
- `DESIGN_PRINCIPLES.md`
  - 面向本 Skill 的开发和维护。
  - 只承载设计原则、实现约束、结构边界、禁止事项。
  - 不承担运行期使用说明。
- `README.md` / `RUNBOOK.md`
  - 作为使用说明、操作说明、维护说明的辅助文档。
  - 不作为架构原则的唯一裁决来源。
- `IMPLEMENTATION_OVERVIEW.md`
  - 面向开发和维护。
  - 用于描述当前实现如何组织、主流程如何落地、关键职责在哪一层实现。
  - 用于和维护者对齐“当前代码实际上怎么工作”，不承担运行期规则裁决职责。

禁止把开发原则塞进 `SKILL.md`，也禁止把运行期交互说明塞进本文件。

## 顶层设计原则

本工程必须同时遵守以下顶层原则：

1. 整个工程结构必须符合 Claude Code 对 Skill 工程的要求。
2. 系统只能有一个业务参数真相源。
3. 系统只能有一个主状态源。
4. `checkpoint` 只是一种流程语义，不保留独立 Checkpoint 文件。
5. 用户回复必须先结构化、归一化、校验，再写入主状态。
6. 后续步骤只能从主状态读取业务参数。
7. 展示文件不得参与任何运行期求值。
8. CLI 不得成为步骤之间透传业务参数的主路径。
9. 任何会改变实现行为、输入输出协议、交互协议、步骤职责或操作方式的程序修改，都必须同步修改对应文档。

## 唯一主状态与唯一参数源

`main_state.json` 是本工程唯一主状态文件，也是唯一业务参数真相源。

`main_state.json` 必须承担以下职责：

- 保存状态机当前状态
- 保存每一步的 `input` / `derived` / `output`
- 保存待交互状态元数据
- 保存已经过确认和归一化的有效业务参数
- 保存恢复执行所需的最小状态信息

一旦业务参数被写入 `main_state.json`，后续步骤必须只从 `main_state.json` 读取，不允许再从其他文件或命令行重新确定真值。

## 删除独立 Checkpoint 文件

本工程不保留独立 `checkpoint` 文件设计。

硬规则如下：

- 不再将 `checkpoint.json` 作为正式设计组成部分。
- `checkpoint` 仅表示“流程可中断、可恢复”的状态语义。
- 所有 checkpoint 相关状态都必须并入 `main_state.json`。
- 不允许新增或恢复独立 `checkpoint.json` 作为运行期状态源。
- 若确有必要临时导出 checkpoint 样式文件，该文件也只能是只读派生产物，不得参与任何运行期求值。

## 文件职责边界

### `main_state.json`

`main_state.json` 是唯一主状态与业务参数来源，负责：

- 当前步骤与已完成步骤
- 当前状态与阻塞原因
- pending interaction 元数据
- 每步输入快照
- 每步派生结果快照
- 每步输出快照
- 已确认的业务参数

### `interaction.json`

`interaction.json` 仅用于展示当前待交互信息，负责：

- 展示问题
- 展示选项
- 展示缺失输入
- 展示建议复核文件
- 展示恢复提示

`interaction.json` 不是状态文件，不是参数文件，不得参与任何运行期求值。

### 报告与证据产物

所有报告、摘要、比对结果、证据文件都属于分析产物，只用于复核与追踪，不得反向作为业务参数真值来源。

### 重跑前清理规则

每一步在重跑前，必须先删除该步骤上一次运行生成的结果产物，避免旧产物混入本轮执行结果。

这里的“结果产物”仅指当前步骤自己生成的分析产物文件或结果目录，不包括：

- `main_state.json`
- `interaction.json`
- 上游步骤产物
- 用户输入文件
- 其他非本步骤生成的状态文件

禁止在重跑前保留当前步骤的旧结果文件并与本轮结果混用。

## 用户输入处理协议

用户输入进入系统后，必须遵守以下顺序：

1. 收集用户原始答复
2. 结构化
3. 归一化
4. 校验
5. 写入 `main_state.json`
6. 从 `main_state.json` 继续后续步骤

禁止以下做法：

- 把用户回复直接作为下一步 CLI 业务参数透传
- 把用户回复仅写入展示文件
- 把用户回复仅保存在临时变量中而不写主状态
- 用户回复已经写入主状态后，又被其他来源覆盖

## 恢复协议

本工程的恢复协议必须遵守以下规则：

- 流程在待交互阶段停下后，恢复动作只能依赖 `main_state.json` 中保存的状态。
- 恢复命令只负责触发继续执行，不负责承载业务参数真值。
- 后续步骤读取的有效参数，必须来自主状态中的当前输入快照，而不是来自恢复命令本身。

允许的恢复路径：

1. 读取主状态中的待交互信息
2. 获取用户答复
3. 将用户答复归一化后写入 `main_state.json`
4. 重新进入对应步骤或继续下一步骤

禁止的恢复路径：

- 通过 CLI 直接携带业务参数继续执行
- 通过展示文件恢复业务参数
- 通过历史产物文件重新拼装当前运行参数

## CLI 边界

CLI 只允许承担以下职责：

- 指定 `project-dir`
- 指定 `report-dir`
- 指定要执行的步骤
- 触发恢复动作
- 指定只影响本次命令调度的流程参数

CLI 不得承担以下职责：

- 在步骤之间透传业务参数真值
- 覆盖已经写入 `main_state.json` 的业务参数
- 与主状态并列成为第二参数源

## 禁止事项

以下做法一律禁止：

- 多源合并业务参数
- 多源合并主状态
- 保留或恢复独立 `checkpoint.json` 作为运行期状态源
- 让 `interaction.json` 参与运行期求值
- 让报告产物参与运行期求值
- 通过 CLI 在步骤之间透传业务参数
- 为了兼容或便利新增第二业务参数入口
- 为了兼容或便利新增第二状态源
- 先实现、后补设计原则
- 修改了程序行为或协议，却不更新对应文档

## 代码评审检查项

每次改动以下区域时，必须逐项检查：

- 是否引入了第二业务参数源
- 是否引入了第二状态源
- 是否让展示文件重新参与求值
- 是否让 CLI 重新成为业务参数主入口
- 是否破坏了“用户回复先入主状态”的协议
- 是否破坏了恢复协议
- 是否破坏了工程结构对 Claude Code Skill 的要求
- 是否把开发原则错误地写进了 `SKILL.md`
- 是否同步更新了受影响的文档（至少检查 `README.md`、`RUNBOOK.md`、`SKILL.md`、`IMPLEMENTATION_OVERVIEW.md`、`DESIGN_PRINCIPLES.md` 中对应职责文档）

## 反例

以下模式属于反例：

- `main_state.json + 第二参数文件 + CLI` 共同决定业务参数真值
- `checkpoint.json` 与 `main_state.json` 同时保存运行期主状态
- `interaction.json` 被后续步骤直接读取为业务参数来源
- 用户回复通过 `--response-json` 直接作为后续步骤业务参数持续透传
- 为了绕过当前设计约束，在局部函数中重新引入隐式默认值或第二入口

## 演进规则

后续若要修改本工程的核心设计原则，必须遵守以下顺序：

1. 先修改本文件
2. 再修改相关实现
3. 再补充或修正回归测试
4. 再更新相关使用说明或运行说明

不允许先落实现，再事后用文档为偏离行为补理由。

对于不直接修改原则、但会改变实现行为、输入输出协议、交互示例、恢复方式、步骤职责或维护方式的普通程序改动，也必须同步更新对应文档；不得把文档更新视为可选收尾工作。

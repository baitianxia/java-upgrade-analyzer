# 工程宪法

本文记录不可被局部实现、性能优化或测试调整破坏的原则。

## 1. 准确性第一

以最终制品、目标 JDK 和显式 RuntimeProfile 为准。不能为速度、流程连续或实现方便缩小范围、降低身份精度、跳过关键证据或隐藏不确定性。

## 2. 根因而非案例特判

反馈是证据，不是结论。修复前确认问题类型、影响阶段和同类实现；修复后检查上游输入、核心处理、下游报告、门禁和平台变体。禁止按项目名、类名或依赖名硬编码。

## 3. 单一 binary 权威

Step4–Step6 只有 binary-first 引擎。源码只能补充解释，不能覆盖制品事实、runtime provider、变化裁决或可执行边。失败关闭并保留上一完整 generation，不调用旧逻辑补算。

## 4. 身份必须完整

变化和路径必须尊重依赖 lineage/coord/version、制品 SHA、owner、member、JVM descriptor、loader realm 和 runtime slot。禁止用裸方法名、简单类名或模糊坐标构造确定链路；重载、同名类和多制品 provider 必须区分。

## 5. 不确定就是不确定

`reachable`、`uncertain`、`not_found_in_static_analysis`、`not_analyzed` 四态不能混淆。静态未发现不等于无影响，静态路径不等于运行时确认。coverage、预算或动态机制不足必须显式限制结论。

## 6. 证据台账完整

`alerts.csv` 覆盖本轮纳入的全部变化 API，不是样例。不同入口或消费者路径应保留；可去除被更完整路径严格包含的重复子路径，但不能丢失独立消费者。每条结果可回溯 generation、变化事实和路径证据。

## 7. 依赖维度不可丢

用户必须知道哪个依赖引起变化。Step4、Step5、Step6 的 Markdown、CSV 和结构化结果都保留依赖坐标以及 base/current 版本；同名 API 不能脱离制品归属展示。

## 8. 用户可见输出先给人看懂

首屏按“范围 → 结论 → 关键原因 → 依赖/API/路径 → 完整明细入口”组织。内部术语应翻译为可操作说明。机器字段可保留，但必须有 Markdown 或清晰摘要；普通复核不能依赖 SQLite、内部 index 或多个缺失关系猜结论。

## 9. 阅读路径连续且目录分层

人工从 Step4 dependency summary 到 Step5 path evidence，再到 Step6 deliverables。机器权威、状态、索引和监控放 `.runtime`；人工证据放 `evidence`；最终交付放 `deliverables`。新增文件必须落在职责明确的目录。

## 10. 交互只用于真实决策

会实质改变分析范围或需要外部事实/授权时才暂停。内部解析、网络、工具和发布问题优先自动重试、修复或失败关闭，不能伪装成用户业务选择。用户确认必须前置，不能让长任务完成后才索要本可提前发现的关键输入。

## 11. 原子、可恢复发布

未验证或半套结果不能成为 active。新 generation 独立写入、独立验证、原子激活；人读目录 stage 后整体替换。失败保留上一有效结果和可追溯失败证据。

## 12. 性能不改变语义

允许内容缓存、索引、有界并行、批量事务和已证明无关的剪枝；禁止抽样 API、少扫依赖、降低匹配精度、静默截断路径或用源码代替 runtime facts。优化必须记录阶段耗时、规模和可取得的内存指标。

## 13. 测试覆盖原则而非旧实现

每项修改有正例、负例和边界例；关键能力包含 archive safety、runtime reconciliation、decision、trace、Oracle、原子发布和用户输出契约。引擎删除时同步删除其专属测试，并把仍有效的原则迁移到当前实现测试，不能靠恢复死代码让测试通过。

## 14. 对比先写真值

分支或引擎 A/B 必须使用相同输入，在看输出前写明预期依赖、变化、路径和边界，再评估漏报、误报与身份错误。只对比数量没有说服力。

## 15. 文档与代码一致

README、Runbook、设计、报告说明和示例只描述实际可执行能力。旧设计如不再有效，应归档或重写，不能与当前架构并列成为维护依据。

## 16. 诚实交付

不得编造执行、测试或性能结果。已验证、未验证、假设和限制分开陈述；局部测试通过不能称全部完成。交付前核对用户要求、全部测试、Git diff、报告可读性和提交状态。

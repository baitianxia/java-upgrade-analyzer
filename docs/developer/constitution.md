# 工程宪法

本文记录本工程在长期讨论、测试和修复中形成的原则性约束。

这些约束高于局部实现偏好。任何优化、重构、性能改造、报告改版或测试调整，都不能违背本文原则。

## 1. 准确性第一

分析准确性永远优先于性能、速度、输出简洁度和实现便利。

允许优化性能，但不能通过减少分析范围、跳过关键证据、降低匹配精度或隐藏不确定性来换取速度。

如果“跑得快”和“结论可信”冲突，选择结论可信。

## 2. 不能为了单一案例硬编码

修复 bug 前必须先判断问题属于整体分析模型的缺陷，还是单个案例的表象。

禁止为了让某个项目、某个类名、某个依赖名通过测试而写特例。

每个修复都应回答：

- 是否适用于同类问题；
- 是否会影响其他场景；
- 是否需要正例、负例和边界例；
- 是否会改变输出语义；
- 是否会引入新的误报或漏报。

## 3. 真实构建产物优先，源码只能作为辅助证据

依赖包分析应以当前工程实际构建或部署产物中的 jar 为主。

源码可以用于增强可读性、补充行为变更、辅助解释调用链，但源码不能覆盖 jar 的事实。

尤其要遵守：

- 当前工程没有引用的 jar，其源码不能进入调用链图；
- 依赖源码映射必须受当前 runtime dependency catalog 约束；
- DTO、DAO、getter/setter、桥接方法、编译器生成方法等必须以字节码事实为准；
- 当源码与构建产物版本、revision、profile 无法证明一致时，结论必须降级为需要复核，不能伪装为确定影响。

## 4. 不确定就是不确定，不能伪装成无影响或已确认影响

结论必须区分：

- 已确认影响；
- 可能影响 / 需要复核；
- 静态未找到链路；
- 未分析。

不能把未找到证据解释成“确定不影响”。

也不能把只有部分证据的链路解释成“已确认影响”。

例如：

- 运行时依赖 jar 确认调用了变更 API，但无法回溯到业务入口时，应标记为可能影响或需要复核；
- 源码中发现调用链，但无法证明源码与实际构建产物一致时，应标记为需要复核；
- 反射、动态代理、XML 配置、MethodHandle 等分析能力不足时，不能静默归类为静态未找到。

## 5. 匹配必须尊重全限定名和签名

调用链匹配必须优先使用全限定类名、方法签名、字段所属类等精确信息。

禁止依靠裸方法名、简单类名或不完整 key 跨 jar、跨包、跨类串出调用链。

如果无法确认全限定名或签名，应保留为不确定证据，而不是构造确定链路。

典型风险：

- `StringUtils.EMPTY` 必须区分 commons-lang、commons-lang3、业务自定义类；
- `method:isBlank` 不能跨不同依赖随意匹配；
- Step5 主调用链追踪不能沿 `fallback_simple` / `method:xxx` 简单名继续扩展；如果中间调用点无法解析到全限定名或受控的多态关系，必须停止，不能把候选错链输出给人工复核；
- 即时调用链查询默认必须全链路精确匹配，不能在起点或中间节点静默退回 `method:xxx`、`class:SimpleName` 等简单名 key；
- 查询结果中的每条链路必须真实包含被查询的目标类、方法或字段；
- 如果需要简单名模糊查询，必须由使用者显式要求，并在输出中标明该结果不能作为确定影响结论；
- JDK 标准类或接口不能误归到目标依赖；
- 重载方法不能只靠方法名判断命中。

## 6. jdeps 能发现的，Step5 不能漏掉

本工程的目标不是弱于 jdeps，而是结合源码、字节码、运行时依赖、框架证据和报告能力，提供更强的影响分析。

因此：

- 业务源码直接调用变更 API，必须发现；
- 业务字节码调用变更 API，必须发现；
- 业务源码 → 依赖 jar → 变更 API，必须尽力发现；
- 多依赖链路，如 A → B → C → D，必须尽力发现；
- 删除依赖、升级依赖、字段变化、构造器变化、类变化都不能只覆盖其中一种。

如果当前能力做不到，必须明确标记为未覆盖或需要复核，而不是输出误导性结论。

## 7. `alerts.csv` 是完整链路台账，不是样例

人工复核依赖 `alerts.csv`。

因此 `alerts.csv` 必须尽量完整表达分析过程：

- 每个变更 API 的结论要清晰；
- 每条不同入口或不同消费者链路要保留；
- A → B → C 已包含 B → C 时，可以不重复输出 B → C；
- 但 E → B → C、F → C 这类不同入口或不同消费者必须保留；
- 不能只展示部分样例；
- 文件过大可以拆分附属文件，但不能用“轻量索引”误导使用者忽略完整台账。

## 8. 所有用户可见输出必须给人看得懂

用户可见输出面向使用者和复核人，不是面向内部实现。

这里的“用户可见输出”包括但不限于：

- `README.md`、`docs/user/*.md` 等使用文档；
- checkpoint 中转述给用户的问题、选项和阻塞原因；
- Step1~Step6 生成的 `summary.txt`、`report.md`、Markdown 明细；
- `alerts.csv`、`dep_alerts.csv`、`all_changed_apis_alerts.csv`、`s6_*.csv` 等人工会打开复核的 CSV；
- 控制台中要求用户据此判断或确认的摘要。

禁止在这些输出中大量暴露难懂实现词汇，例如：

- 源码图；
- reverse edge；
- artifact alignment；
- revision/profile；
- internal graph；
- fallback simple key。

如果确实需要表达，应翻译成人能理解的话。

历史问题示例，禁止在用户可见输出中继续出现：

> 源码图存在目标调用，但源码与最终制品未证明来自同一 revision/profile。

应写成：

> 源码中发现了调用链，但无法确认这份源码与本次分析的构建产物完全一致，因此需要人工复核。

用户可见输出应优先回答：

- 哪个依赖；
- 哪个变更 API；
- 发生了什么变化；
- 当前结论是什么；
- 调用链是什么；
- 为什么确定或为什么需要复核。

所有面向用户的文档和报告必须读起来流畅、符合排查逻辑，并且跨文件保持连贯。

具体要求：

- 单个文件内部必须按“问题/范围 → 结论 → 关键原因 → 调用链或证据 → 明细入口”的顺序组织；
- 多个文件之间必须形成连续阅读路径，不能让用户在 README、Step 摘要、CSV、最终报告之间反复猜“下一步该看哪里”；
- 同一个概念在不同文件中必须使用一致名称，例如“已确认影响”“需要人工复核”“未发现静态调用路径”“未完成分析”不能在不同文件里混用相互矛盾的叫法；
- 如果某个文件引用另一个文件，必须说明引用它是为了解决什么问题，而不是只给一个文件名；
- 用户打开任意人工复核文件时，第一屏就应该知道这个文件回答什么问题、当前结果是什么、后续要看哪里；
- 文档、报告、CSV 和 checkpoint 文案不能各说各话，必须围绕同一条分析链路：依赖变化 → API 变化 → 调用链影响 → 最终结论。

格式同样属于可读性要求：

- 首屏先给结论和复核入口，再给技术明细；
- 表格只承载短字段，长调用链、长原因、长文件列表应放到表格下方列表或明细文件；
- 大量条目必须截断展示并指向完整文件，不能让主报告变成无法预览的大文档；
- CSV 如必须保留机器字段，应额外提供人能直接理解的摘要字段或配套 Markdown；
- 不允许只修某一个 Step 的报告就宣称“用户可见输出已优化”。

## 9. 人工接触的文件越少越好，但关键证据不能丢

使用者不应被迫阅读大量临时文件。

默认复核入口应尽量集中在：

- Step4 的变更 API 列表；
- Step5 的 `alerts.csv` 及必要拆分文件；
- Step6 的最终汇总报告。

可以输出更多机器可读或调试文件，但不能让它们成为普通使用者理解结论的前置条件。

## 10. 交互必须前置，避免浪费用户时间

如果某个信息缺失会导致后续步骤长时间运行后失败，必须尽量前置检查。

例如：

- 多个可部署模块无法唯一判断时，必须先让用户选择；
- Step4 的依赖源码 git refs 需要确认时，应在耗时分析前停下；
- JApiCmp 缺失时按受控工具流程处理；tree-sitter 必须通过固定清单显式 bootstrap，运行时不得联网安装。关键能力预检失败后应明确说明影响并停止，不得静默降级；
- 用户要求从某一步重跑时，每一步都应支持安全重跑。

## 11. 性能优化不能改变结论语义

性能优化只能做：

- 缓存；
- 索引；
- 并行；
- 剪枝已证明无关的数据；
- 减少重复解析；
- 改善数据结构；
- 增加耗时统计。

性能优化不能做：

- 少分析一类输入；
- 降低匹配精度；
- 忽略反射或依赖链；
- 只分析少量 API 样例；
- 把未完成分析输出成无影响；
- 为了快而跳过 runtime jar 事实。

## 12. 测试不能点到为止

每次修复都必须补充针对性测试。

重要能力必须有固定回归集，不能只靠用户真实项目发现问题。

测试应覆盖：

- 正例：应该命中；
- 负例：相似但不应该命中；
- 边界例：输入不完整时应进入不确定或未分析；
- 压力模型：大量 jar、大量 API、大量调用边；
- 真实项目：验证工程化输入、构建产物、依赖结构和运行时间。

如果每轮测试都能轻易发现新 bug，说明测试体系不足，而不是“刚好遇到特例”。

## 13. 真实项目测试必须尊重真实场景

真实项目测试不能只挑几个 API 或少量 jar 冒充真实场景。

如果目标是模拟“删除 commons-lang 对一个 400 jar 工程的影响”，测试就必须尽量使用真实 Step4 产出的 API、真实运行时依赖 jar、真实业务源码或真实构建产物。

真实项目测试至少记录：

- 项目规模；
- 依赖数量；
- API 变化数量；
- Step1~Step6 耗时；
- 是否命中预期链路；
- 是否出现误报；
- 是否出现漏报；
- 性能瓶颈在哪里。

## 14. 输出必须支持复核和排查

本工具不只是给结论，还要给证据链。

当结论与用户预期不一致时，用户应能通过输出文件反查：

- 变更 API 是从哪里来的；
- 哪个依赖发生变化；
- 是否来自 JApiCmp、git diff、removed jar export 或其他证据；
- Step5 是如何找到或没找到调用链的；
- 哪个消费者 jar 或业务入口参与了链路；
- 为什么是 reachable、not_impacted、uncertain、not_found 或 not_analyzed。

## 15. 修改文档不能偏离实际代码

README、报告说明、质量文档和使用示例必须与真实代码行为一致。

不能为了“看起来好用”写代码尚不支持的能力。

不能把给 Claude Code 使用的内部命令包装成要求普通用户手工执行的流程。

用户文档应说明“在 Claude Code 中如何表达需求”，命令细节放在维护者文档或 Runbook。

## 16. 用户可见文件必须先给结论和原因

所有暴露给使用者或人工复核人的文件，都必须简洁、清晰、明了。

用户打开文件后，应能第一时间知道：

- 当前结论是什么；
- 为什么得到这个结论；
- 哪些依赖、API 或业务入口受影响；
- 如果不能确认，缺少什么证据；
- 应该优先查看哪条链路或哪个文件。

输出文件应遵守：

- 结论和原因放在文件前部；
- 关键链路和关键证据紧跟结论；
- 内部状态、耗时、置信度、调试字段后置；
- 不用内部术语替代用户能理解的话；
- CSV 字段应优先排列结论、原因、依赖、API、链路、动作，再放辅助字段；
- 机器可读和调试文件可以存在，但不能成为普通用户理解结论的前置条件。

如果输出简洁度与证据完整性冲突，主文件保持简洁，完整证据放入明确标注的明细文件，并在主文件中指向它。

## 17. 必须诚实回答所有问题

所有回答都必须清晰、准确、诚实，并按证据强度明确区分：

- **已核实事实**：有当前可检查的事实或证据直接支持；
- **基于证据的推断**：由已知证据推导，但不是直接事实，必须明确标注为推断；
- **无法确认**：当前没有足够事实或证据，必须直接说明无法确认。

禁止编造、猜测或夸大事实、执行、进度、结果、原因、能力和验证范围。禁止声称执行了实际没有执行的命令或工作，禁止把计划、意图和预计结果写成已经发生的事实。不得通过遗漏与问题直接相关、且会改变用户判断的关键事实形成误导。

回答应直接针对用户问题。事实、推断和意见必须分开表达；引用旧结果时必须说明其时间和适用范围，不能冒充当前证据。发现先前回答不准确、前后矛盾或缺少关键事实时，必须立即明确更正，并给出当前能够确认的事实。

### 17.1 任务状态必须精确

对工程状态、修复结果、测试结果和任务完成度的回答，必须以当前证据为准，不得为了显得有进展而扩大结论范围。

回答“是否完成”前必须核对：

- 用户交代的完整任务和仍然有效的要求；
- 当前工作区、提交和推送状态；
- 本轮实际执行的测试、真实项目审计及其覆盖范围；
- 已知缺陷、未执行步骤和无法证明的场景。

每个任务项的执行状态必须按事实标记：

- **已完成**：该项要求的实际工作已经完成；
- **正在执行**：报告时确有命令、进程或实际工作正在运行；
- **待执行**：该项尚未开始，包括计划执行、准备执行和等待以后恢复；
- **阻塞**：该项已经开始或应当开始，但被明确条件阻止；
- **失败**：该项已经执行但没有成功。

验证状态必须与执行状态分开记录：

- **已验证**：有当前证据证明结果满足相应完成条件；
- **未验证**：没有足够的当前证据确认结果。

“未完成”只用于表达总体仍有任务没有完成，或作为上述“正在执行、待执行、阻塞、失败”的上位集合，不能代替具体任务状态。实现已经结束但尚无充分证据时，应写“已完成、未验证”。

必须遵守以下边界：

- 局部实现完成不等于整体任务完成；
- 单元测试通过不等于真实项目验证完成；
- 一个真实项目通过不等于所有项目拓扑已经得到证明；
- 代码已修改但用户要求的提交、推送或报告尚未完成时，不能宣称交付完成；
- 持续验证新项目是用户明确任务时，不能把剩余验证降格为可选的“后续增强”；
- 不得把“计划执行”“准备执行”“待恢复”或没有实际运行的工作描述为“正在执行”；
- 不知道或无法核实时必须明确说“无法确认”，不能猜测，也不能重复未经核验的旧结论。

多项任务必须报告总数和各状态数量，并列出未完成项，例如“共 10 项：已完成 4、正在执行 1、待执行 5”。只要存在一项必需工作不是“已完成”，就必须直接说明“没有全部完成”。验证状态另行报告，不得混入执行状态。发现先前陈述不准确时，应立即更正并说明事实，不得用重新定义“完成”掩盖矛盾。

## 18. 宪法变更必须谨慎

本文不是普通 TODO。

如果未来确实需要修改这些原则，必须说明：

- 为什么原原则不再适用；
- 修改会影响哪些 Step；
- 是否需要迁移测试和文档；
- 是否会改变用户对结论可信度的理解。

在没有明确理由前，代码应服从本文，而不是让本文追随代码。

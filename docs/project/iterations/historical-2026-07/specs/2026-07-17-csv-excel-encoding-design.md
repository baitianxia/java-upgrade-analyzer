# CSV Excel 编码统一设计

## 目标

工程生成的所有 CSV 文件统一使用带 UTF-8 BOM 的编码，使用户在 Windows 和 macOS 上直接用 Excel 打开时可以正确显示中文。同时保证 Step1 到 Step6、即时调用链查询、质量门禁和回归工具仍能稳定读取这些文件。

## 编码契约

- 所有 CSV 写入统一使用 Python 编码名 `utf-8-sig`。
- 所有 CSV 读取统一使用 `utf-8-sig`。该编码可以同时读取带 BOM 的新文件和不带 BOM 的历史 UTF-8 文件。
- JSON、Markdown、文本日志、源码和二进制缓存不改变编码，继续使用 UTF-8 或其现有格式。
- CSV 首行只能有一个 UTF-8 BOM；文件正文及追加内容中不得出现额外 BOM。
- 空 CSV 仍必须包含 BOM 和完整表头，不能生成零字节文件。

## 覆盖范围

范围包括所有由工程脚本生成的 `.csv`：

- Step1 依赖清单与告警；
- Step3 静态扫描结果；
- Step4 API 变化清单、告警与辅助明细；
- Step5 `alerts.csv`、拆分台账、性能明细和字节码证据；
- Step6 分类明细；
- `.runtime/observability` 下的耗时统计；
- 质量门禁、Oracle、真实项目回归和用户场景回归产生的 CSV；
- 临时筛选文件和缓存目录中的 CSV。

测试自身创建的输入 CSV 也统一通过相同契约生成，避免测试只覆盖纯 UTF-8、真实运行却使用 BOM 的偏差。

## 写入设计

新增公共 CSV 编码常量和打开函数，作为生产代码的默认入口：

- 覆盖写：以 `utf-8-sig`、`newline=""` 打开；
- 读取：以 `utf-8-sig`、`newline=""` 打开；
- 追加写：若文件不存在或为空，使用 `utf-8-sig` 创建并写入一次 BOM；若文件已有内容，以普通 `utf-8` 追加，防止编码器在文件中间再次写入 BOM。

不能直接将所有 `open(..., encoding="utf-8")` 机械替换为 `utf-8-sig`，因为追加模式需要单独处理，且非 CSV 文件不在本次范围内。

## 读取兼容性

工程内所有 CSV 读取入口改为 `utf-8-sig`：

- 新文件的 BOM 会被透明移除，首列表头保持为 `coord`、`api_name` 等真实字段名；
- 历史纯 UTF-8 CSV 仍可读取；
- 中文、英文和符号内容保持原值；
- 不对 GBK 等非 UTF-8 历史文件进行猜测性降级，避免错误解码被当作有效证据。

## 错误处理

- 遇到非法 UTF-8 CSV 时保持现有失败或证据不完整语义，不静默改用本地编码。
- 公共追加函数检测正文中出现 BOM 时应通过测试暴露，不自动吞掉数据污染。
- 任何下游读取到带 `\ufeff` 的表头都视为编码契约失败。

## 验证方案

1. 单元测试验证所有公共写入模式的前三个字节为 `EF BB BF`。
2. 验证中文表头和中文单元格用 `utf-8-sig`、Excel 兼容方式均可正确读取。
3. 验证纯 UTF-8 历史 CSV 可由新读取入口读取。
4. 验证追加两次后文件只有一个 BOM，且无正文 BOM。
5. 静态契约测试扫描生产脚本，禁止直接以纯 `utf-8` 写入 `.csv`。
6. 运行 Step1→Step6 核心冒烟、orchestrator 回归和完整单元测试。
7. 抽查 `dep_changes.csv`、`all_changed_apis.csv`、`alerts.csv`、Step6 分类 CSV 和 observability CSV 的原始字节及首列表头。

## 非目标

- 不新增 `.xlsx` 文件。
- 不改变 CSV 字段、排序、路径和业务语义。
- 不为非 UTF-8 历史 CSV 增加编码探测。
- 不改变用户需要接触的文件数量。

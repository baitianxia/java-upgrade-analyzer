# Step5 等价降内存设计

## 目标

降低 Step5 在大型 Java 工程中的峰值内存，避免系统内存压力连带导致 IntelliJ 崩溃，同时满足两个不可妥协的约束：

1. 分析结果不得变化，包括 API 状态、调用链节点与顺序、证据、覆盖状态和用户报告。
2. 同一输入下的运行时间不得增加；以重复运行的中位耗时作为验收依据。

## 已确认的内存放大点

当前实现会在证据收集、间接用法分析和框架证据合并阶段保留或构造同一调用边的多种内存表示：

- `_graph_snapshot_with_bytecode_batch` 复制完整 `reverse_edges` 字典和每个边列表。
- 框架投影前再次复制完整 `reverse_edges`。
- `sorted(batch.edges)` 为整个批次创建排序列表。
- 合并过程同时持有 collector batch、`accepted_edges`、去重集合、转换后的调用边和 evidence registry。
- 阶段结束后，临时 batch 和索引没有在最后一次使用后立即释放。

这些结构不增加分析事实，只增加同一事实的并存副本和生命周期。

## 设计

### 1. 间接分析使用只读叠加视图

保留原始 `graph.reverse_edges` 作为基础映射，只为字节码反射边建立小型 overlay。读取某个 key 时返回基础边与 overlay 边的只读组合，不复制其他 key 或列表。

视图只实现间接分析器实际使用的读取接口。任何写入尝试都必须失败，避免分析期间改变主图。

### 2. 框架投影使用按需快照

框架投影只冻结本轮框架记录实际会查询的 source keys。投影逻辑在加入框架语义边前确定所需 key，并仅复制这些 key 对应的边列表。

如果无法证明查询 key 集合完整，则保留原实现并将该项视为未完成，不能用不完整快照换取内存下降。

### 3. 缩短临时对象生命周期

每个 batch 的覆盖信息、失败信息和统计提取完成后，立即解除局部引用。框架序列化产物写完后不继续保留仅用于输出的临时映射。

不得通过删除调用图、证据台账或用户可复核信息降低内存。只释放后续阶段不再读取的对象。

### 4. 避免无条件排序副本

collector 输出必须具有确定顺序。合并边界先验证输入是否已经按稳定 identity 排序：

- 已排序：直接迭代原 tuple。
- 未排序：沿用当前 `sorted` 行为。

该优化不能改变结果顺序，也不能取消去重。

### 5. 内存可观测性

在以下阶段记录当前 RSS、进程峰值 RSS、方法数、反向边 key 数和边数量：

- 业务源码图完成；
- 依赖源码图完成；
- 业务字节码收集完成；
- 间接用法收集完成；
- 框架/字节码证据合并完成；
- 调用链追踪完成。

指标进入 Step5 observability 产物和过程日志。指标采集失败只能记录不可用，不能影响分析。

## 明确不采用

- 不降低 `max_depth` 或 `max_methods`。
- 不减少扫描的 JAR、class、API 或框架适配器。
- 不因内存压力把明确结论降级为 `uncertain` 或 `not_analyzed`。
- 不采用会增加 I/O 的 SQLite、磁盘分页或外部排序作为本轮默认实现。
- 不以硬杀进程作为内存控制方案。

## 正确性验证

建立优化前基线并对优化后结果进行语义和顺序对比：

- 每个 API 的最终状态及 reason code；
- 每条调用链的入口、每一跳、终点、证据类型和证据文件；
- `alerts.csv`、Step5 `summary.json` 和 Step6 关键结论；
- framework、bytecode、indirect collector 的合并、重复和拒绝计数；
- 即时调用链查询结果。

除新增内存观测字段外，既有输出必须完全一致。

## 性能验收

使用固定的大规模合成图和真实 Dubbo 回归案例分别运行优化前、优化后版本：

- 每个版本至少重复三次，比较中位总耗时和各阶段耗时。
- 优化后中位总耗时不得高于优化前。
- 峰值 RSS 必须下降；若只改变测量方式而没有降低峰值，不视为完成。
- 完整单元测试、核心冒烟测试和真实项目结果审查全部通过后才允许提交实现。

## 回退原则

每个内存优化点独立提交和验证。任何一项造成结果差异、运行时间增加或证据缺失，都单独回退，不用后续优化掩盖问题。

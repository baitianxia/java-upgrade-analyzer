# Step5 依赖源码版本对齐设计

## 背景

Step4 已能把依赖版本解析为用于源码对比的 `old_ref/new_ref`，但 Step5 当前只接收“依赖坐标 = 本地目录”的映射，并直接扫描该目录当前工作区中的源码。若本地工作区分支与当前运行时 JAR 对应版本不同，源码图可能包含错误实现、错误方法或未打包模块，进而造成误关联或漏报。

依赖分析必须继续遵守以下原则：

1. 当前最终制品中的 JAR 和 class 是主要事实源。
2. 依赖源码只用于补充方法体、框架配置和可读调用关系，不能扩大最终制品的实际范围。
3. 无法证明源码版本与 JAR 对齐时，宁可停止使用该源码，也不能静默使用本地当前分支。
4. 不切换、不清理、不修改用户的依赖源码工作区。

## 目标

1. Step5 对每个依赖源码映射使用 Step4 已确认的当前版本 ref，而不是用户工作区当前 HEAD。
2. 在隔离的 detached worktree 中解析依赖源码，不修改用户分支和未提交文件。
3. 只有同时属于当前运行时依赖坐标、且类存在于对应运行时 JAR 的源码才能进入调用图。
4. ref 缺失、解析冲突、快照失败或 JAR 校验失败时，禁止使用未经验证的本地源码。
5. 保留 JAR 字节码分析能力；只有 JAR 证据也不足时才进入现有缺少输入或 `not_analyzed` 流程。
6. 输出机器可读且人类可理解的版本对齐证据。

## 输入事实源

### Step4 ref 证据

Step5 读取：

```text
evidence/api_changes/git_ref_matches.json
```

每个可使用的依赖必须唯一匹配以下信息：

- `coord`
- `repo_path`
- `module_rel_path`
- `resolved_new_ref`，兼容读取同一记录中的 `cur_ref`
- ref 解析状态必须为 `matched` 或来自成功的 git diff 记录

如果同一依赖存在多个不同的当前 ref、仓库路径或模块路径，视为冲突，不选择任意一个。

### 当前运行时 JAR

JAR 路径继续来自 Step1 最终制品目录和 Step5 的 `runtime_dependency_catalog`。源码快照不能替代该目录，也不能把目录之外的依赖或类加入分析范围。

## 隔离快照

### 创建方式

对通过 ref 校验的 Git 依赖仓库执行：

```text
git -C <repo> worktree add --detach <snapshot-path> <resolved-commit>
```

先用 `git rev-parse <ref>^{commit}` 固定为 commit SHA，避免同名分支在分析期间移动。快照位于报告内部目录：

```text
.runtime/source_snapshots/<安全坐标>/<commit-short>/
```

Step5 重跑时，如果快照目录存在且 HEAD 等于目标 commit，则直接复用。目录存在但 commit 不一致、不是有效 worktree 或内容不完整时，不复用，也不使用其中源码。

### 工作区保护

快照创建前后记录用户仓库的：

- 当前分支名
- HEAD commit
- `git status --porcelain` 摘要

Step5 不执行 `checkout`、`switch`、`reset`、`clean` 或 stash。快照完成后重新检查上述信息；只要 HEAD、分支或工作区状态发生变化，就将该依赖源码标记为对齐失败并停止使用。

### 模块路径

Step4 的 `module_rel_path` 相对于 `repo_path` 应用到快照根目录。Step5 只从该模块下发现标准生产源码目录，不扫描仓库中的其他模块。无法安全解析相对路径、路径逃逸快照根目录或目标模块不存在时，对齐失败。

## JAR 范围校验

### 坐标过滤

沿用当前运行时坐标过滤：只有存在于 `runtime_dependency_catalog` 的依赖坐标才保留源码映射。

### 类过滤

为每个运行时依赖 JAR 单独建立类全限定名集合。分析依赖源码文件时：

1. 从 package 和顶层类型声明计算源码类全限定名。
2. 该类必须存在于同坐标的运行时 JAR。
3. 不存在于 JAR 的源码类、整个未打包模块以及它们产生的方法和调用边全部跳过。
4. 同名类只允许与同一依赖坐标的 JAR 对齐，不能使用全局类名集合跨依赖证明存在性。

JAR 中存在、源码中不存在的编译生成方法继续由 classfile/JAR 字节码分析覆盖；不能因为源码缺少 getter、setter、DTO 或 DAO 生成方法就把它们判断为删除。

## 失败处理

依赖源码发生以下任一情况时，不进入源码图：

- Step4 没有唯一的当前版本 ref；
- ref 不能解析为 commit；
- ref 记录的仓库与用户映射仓库不一致；
- detached worktree 创建或复用失败；
- 模块路径无效；
- 用户工作区在快照过程中发生变化；
- 对应运行时 JAR 不存在；
- JAR 类索引构建失败，无法完成按坐标类过滤。

失败后：

1. 保留当前最终制品的业务字节码和运行时依赖 JAR 分析。
2. 将失败依赖从 `dependency_source_mappings` 中移除，不能回退使用原始本地目录。
3. 若 JAR 字节码能够形成证据，按现有五态输出。
4. 若某 API 必须依赖源码才能完成分析且没有完整 JAR 证据，进入现有交互或 `not_analyzed`，原因明确为依赖源码版本无法对齐。
5. 不允许使用 `--allow-degraded` 把错误版本源码重新加入调用图；降级只表示放弃该源码并继续使用可靠 JAR 证据。

## 证据输出

新增内部证据文件：

```text
evidence/call_chain/dependency_source_alignment.json
```

每个依赖记录：

- 坐标和运行时 JAR 版本
- 原始映射路径
- Step4 选定 ref
- 固定 commit SHA
- 隔离快照路径
- 模块相对路径和实际生产源码根
- JAR 类数量、保留源码类数量、跳过源码类数量
- `aligned / rejected / unavailable` 状态
- 面向人的失败原因和内部 reason code
- 用户工作区前后 HEAD、分支、dirty 状态是否一致

Step6 不新增必须阅读的文件。只有依赖源码对齐失败实际影响某项分析结论时，现有报告的“证据摘要 / 未确认原因”才以人话说明该问题。

## 生命周期

快照是 `.runtime` 内部可重建缓存，不提交到 Git，也不作为交付文件。Step5 重跑优先复用 commit 一致的快照。本次实现不自动删除用户仓库已经注册的其他 worktree，也不清理用户目录。

## 与现有修复的关系

本次实现必须保留：

1. 所有方法共享 `known_classes_by_simple` 只读索引，禁止恢复每方法 `dict(...)` 拷贝。
2. 变更 API 起点必须使用全限定名和精确签名。
3. 主调用链不得通过 `fallback_simple` 扩展。
4. 依赖源码中缺少全限定名或方法签名的边不得进入反向索引。

## 测试与验收

至少覆盖：

1. 用户仓库当前分支为 A、Step4 `new_ref` 为 B 时，Step5 只解析 B 的源码。
2. 快照创建前后用户仓库分支、HEAD 和未提交文件完全不变。
3. 同一 ref 重跑复用正确快照。
4. ref 缺失、冲突和不存在时拒绝本地当前分支源码。
5. `module_rel_path` 只能解析到快照内部目标模块。
6. 当前分支存在但目标 ref 不存在的类不能进入图。
7. 目标 ref 存在但当前运行时 JAR 未打包的类和模块不能进入图。
8. JAR 中编译生成、源码中不存在的方法仍由字节码证据识别。
9. 多个依赖不同坐标下的同名类不发生类存在性串用。
10. `commons-lang` 与 `commons-lang3` 的同名类、同名方法不串链。
11. 所有方法继续共享同一 class-resolution 索引对象，防止 O(N×M) 内存回归。
12. Step4 ref 预检、Step5 全量测试和真实多分支 Git 项目回归通过。

验收标准：只要依赖源码没有被证明来自 Step4 确认的当前版本 commit 且属于当前运行时 JAR 范围，就不能参与 Step5 调用链结论。

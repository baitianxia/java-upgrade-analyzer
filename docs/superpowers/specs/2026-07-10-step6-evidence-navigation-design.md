# Step6 API 证据导航设计

## 背景

Step6 主报告当前已经使用以下五列表格汇总 API 分析结果：

| 依赖坐标 | 变更 API | 变化 | 结论 | 证据摘要 / 未确认原因 |
|---|---|---|---|---|

这个结构适合一次包含大量依赖和变更 API 的分析，应当保留。当前问题是最后一列只给出“已确认链路 1 条；另有 267 条依赖引用尚未回溯到业务入口”等数量，读者不能立即知道具体链路在哪里，也不知道如何区分已确认链路和未确认引用。

## 目标

1. 保留现有五列及其顺序，不增加主表列。
2. 让存在调用证据的表格行可以直接跳到同一份报告内的对应证据说明。
3. 在证据说明中同时展示具体链路和完整证据的精确定位方法。
4. 不新增用户必须接触的报告文件，完整逐链路台账仍以 `evidence/call_chain/alerts.csv` 为准。
5. 控制报告体积，不把大量完整路径重复写入 Step6 主报告。

## 报告结构

### 主结果表

主表继续使用既有五列。只调整“证据摘要 / 未确认原因”的内容：

- `reachable`：显示已确认链路数和其他未回溯引用数，并提供“查看具体链路”链接。
- `uncertain`：说明发现了多少条依赖引用、为何尚未确认，并提供“查看引用详情”链接。
- `not_found_in_static_analysis`：直接说明已经检查的证据范围和未发现链路的结论，不生成无意义链接。
- `not_analyzed`：直接说明未完成分析的具体原因；只有确实存在可展示证据时才生成链接。

示例：

```markdown
| `org.slf4j:slf4j-api` | `org.slf4j.Logger` | 类被删除 | **已确认影响** | [已确认链路 1 条；另有 267 条依赖引用尚未回溯到业务入口。查看具体链路](#api-api-a57bdec43eeb) |
```

### 同报告内的证据说明

对主表中存在调用证据的 API，在表格之后生成唯一锚点。锚点使用稳定的 `api_id`，格式为 `api-<规范化 api_id>`，避免同名类、重载方法和不同依赖之间发生跳转冲突。报告必须输出 `<a id="..."></a>` 显式锚点，不能依赖 Markdown 渲染器自动推导标题锚点。

每个证据说明包含：

1. 变更 API 的完整签名和 API 编号。
2. 已确认链路数量及当前报告内展示的具体链路。
3. 尚未回溯到业务入口的依赖引用数量及当前报告内展示的具体引用。
4. 完整证据文件路径和精确筛选条件。

示例：

```markdown
<a id="api-api-a57bdec43eeb"></a>

### `org.slf4j.Logger` 的调用链证据

- API 编号：`API-a57bdec43eeb`
- 已确认链路：1 条
- 尚未回溯到业务入口的依赖引用：267 条

已确认链路：

    org.apache.dubbo.springboot.demo.consumer.ConsumerApplication.<class>
    → org.slf4j.Logger

完整证据：打开 `evidence/call_chain/alerts.csv`，筛选
`api_id = API-a57bdec43eeb`。其中 `path_status = reachable` 是已确认链路，
`path_status = uncertain` 是尚未回溯到业务入口的依赖引用。
```

报告内沿用现有路径展示上限，防止单个 API 的数百条引用再次把主报告撑大。超过展示上限时必须明确写出“当前展示 X 条，共 Y 条”，并给出上述 CSV 精确筛选条件；不得使用没有总数和定位方法的“部分样例”表述。

## 数据流

1. Step6 读取 `alerts.csv` 时，按现有 API 身份键聚合路径，同时保留该 API 的稳定 `api_id`。
2. API 结果行取得聚合后的 `api_id`、各 `path_status` 数量和代表性路径。
3. 主表的证据摘要根据状态生成普通文本或带锚点链接的文本。
4. 证据说明使用相同的 `api_id` 生成显式锚点和 CSV 筛选提示。
5. 主表链接与证据说明共用一个锚点生成函数，避免链接和目标不一致。

如果输入行缺少 `api_id`，Step6 不得用简单类名或方法名猜测关联关系。只有通过当前的完整 API 身份键唯一关联到 alerts 记录时才补入 `api_id`；无法唯一关联时保留清晰摘要，但不生成错误链接。

## 兼容性与边界

- 不改变 Step5 的结论、路径状态和证据内容。
- 不改变 Step6 主表列名、列顺序和 API 排序。
- 不新增交付文件，不改变 `alerts.csv` 的字段和拆分规则。
- 不为静态未找到链路的 API 创建空证据章节。
- Markdown 链接文本必须是完整的人类可读结论，不能只显示 `API-...` 或 `path_status`。
- CSV 筛选条件保留原始字段和值，保证人工可以准确复核。

## 测试与验收

实现采用测试先行，至少覆盖：

1. 保留五列表头及原有顺序。
2. 已确认影响行显示已确认和未确认数量，并链接到正确 `api_id` 锚点。
3. 无法静态确认行链接到正确证据说明。
4. 同名类、重载方法和不同依赖的链接互不串线。
5. 返回的证据说明包含目标 API、实际路径和 `alerts.csv` 精确筛选条件。
6. 静态未找到链路不生成空链接或空证据章节。
7. 缺失或无法唯一关联 `api_id` 时不进行模糊匹配。
8. 路径数量超过报告展示上限时，显示“当前展示 X 条，共 Y 条”和完整定位方法。
9. 现有 Step6 报告测试、完整自动化测试以及一份真实 Dubbo 结果报告生成均通过。

验收时，读者应当能够从任意一条存在证据的主表记录，通过一次点击看到具体链路，并能依据报告给出的 `api_id` 和 `path_status` 在 `alerts.csv` 中定位全部证据。
